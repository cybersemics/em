# When a blur, a blend, or a z-index silently does nothing

## Context

`backdrop-filter` filters only what is painted behind it *within its own stacking context*; `mix-blend-mode` blends only against a backdrop the engine has actually composited; a `z-index` ranks only against siblings in the same context. Four incidents across the gesture and Command Center surfaces looked like layout bugs and were all one of those three sentences: the declaration was right and the box around it was wrong.

So the first two questions are never about the declaration:

1. **Which stacking context is this element in, relative to the thing it is supposed to affect?** Anything that forms one — a positioned element with a z-index, `opacity < 1`, `isolation`, `mix-blend-mode`, a `transform` — seals its subtree into a single layer at its own rank. From outside, the z-indexes inside it mean nothing.
2. **Did the element get its own compositing layer, and did it keep it?** Engines promote by their own rules, and a blend against a backdrop that was never composited, or a layer dropped for one frame, fails silently.

| Surface | Symptom | What was actually wrong |
| --- | --- | --- |
| Gesture Menu (#3791, #4466) | The gesture trace drew blurry under the menu. | The blur was nested inside `PopupBase`, whose `popup` rank seals it. No z-index on the trace could order against it. [`GestureContentBlur`](../../../src/components/GestureMenu/GestureContentBlur.tsx) is now a *sibling* of `PopupBase`, mounted from [`GestureMenu.tsx`](../../../src/components/GestureMenu/GestureMenu.tsx). |
| NavBar over the gesture layers (#4466) | The NavBar painted above the blur and the trace, which rank far above `navbar` in the schedule. | react-native-web's `<View>` emits `position: relative; z-index: 0`, so everything inside [`MultiGesture`](../../../src/components/MultiGesture.tsx) was one layer at rank 0 in the root context. Its `render` now sets `zIndex: 'auto'` to dissolve the box. |
| Gesture Menu on Android WebView (#4466) | At the end of the menu's fade-out the blur flashed through the menu for a frame. | The WebView dropped the fading subtree's compositor layer as the opacity surface collapsed. The overlay in `GestureMenu.tsx` carries `willChange: 'opacity'` to keep it alive. |
| Command Center active-button glow on Android WebView (#3936) | The glow smeared, and the blend composited to a solid black box over the dark canvas. | A runtime `filter: blur()` under a `mix-blend-mode` on one node corrupted Chromium's compositor, and the HSL blends are darkening modes. [`PanelCommand`](../../../src/components/CommandCenter/PanelCommand.tsx) now uses a single `plus-lighter` layer — separable and additive, so it can never darken — over a pre-baked, pre-blurred asset: no runtime filter, no HSL blend, no platform branch. |

## Guidance

**Nesting is what makes a z-index token mean anything.** The schedule in [`panda.config.ts`](../../../panda.config.ts) — the `zIndex` block under `tokens`, generated by `zIndexDescending` — ranks every layer in the app in one place, and a token only ranks against the others that share a context with it. Placing a layer as a child of a higher-ranked box hands it that box's rank and discards its own. That is why `GestureContentBlur` is a sibling of `PopupBase` rather than a child, and why `MultiGesture`'s `<View>` had to stop forming a context: both comments say so at their sites, but neither says that the two are the same fix applied to a different pair.

**When a layer has to order against something outside its parent, move it out into the shared context and give it a token there.** The tempting opposite — avoid z-index, because adding one creates a context that breaks blending — is not what shipped. [`CommandCenter.tsx`](../../../src/components/CommandCenter/CommandCenter.tsx) sets `zIndex: token('zIndex.commandCenter')` on the `<Sheet>` *and* `zIndex: 'commandCenterBlur'` on the blur, with the blur deliberately placed outside the Sheet so the fixed-position parent cannot separate it from the background content. The layer that must blend is the one that moves.

**Forming a context on purpose is the other half of the rule.** The Gesture Menu overlay sets `isolation: 'isolate'` so its own `mix-blend-mode` and `backdrop-filter` cannot reach each other — a stacking context used as a wall rather than tripped over.

**`will-change` is a measured workaround, not a habit.** Both live uses name the engine and the failure in the comment beside them. `willChange: 'opacity'` in `GestureMenu.tsx` holds a layer through a fade Android WebView would otherwise drop. `promoteLayers` on [`ProgressiveBlur`](../../../src/components/ProgressiveBlur.tsx) caches each layer's rasterised `backdrop-filter` output instead of re-blurring on every repaint — measured at 51→74 fps for the sidebar blur on Android in #3936 — and is passed only as `promoteLayers={isAndroid}` from [`SidebarBackground`](../../../src/components/Sidebar/SidebarBackground.tsx), because on iOS promoted layers grow the WebKit GPU process toward the jetsam limit. The same pull request had already stripped a blanket set of these hacks out of `ProgressiveBlur` for memory before reintroducing this one behind an opt-in prop.

Two `backdrop-filter` constraints are stated in `ProgressiveBlur`'s prop JSDoc and are easy to hit from outside it: animating opacity on a *parent* of backdrop-filter elements breaks the blur in WebKit (drive a `MotionValue` through the `opacity` prop instead, applied per layer), and a mask on a parent does not apply to backdrop-filter (pass `mask` and let it compose per layer with `maskComposite: 'intersect'`).

## Why This Matters

Nothing in [`docs/`](../../readme.md) describes paint order — z-index, stacking contexts, `backdrop-filter`, `mix-blend-mode` and `will-change` appear in none of it. [`layout-rendering.md`](../../layout-rendering.md) is the doc a reader reaches for and it covers positioning and sizing — `usePositionedThoughts`, autocrop, virtualization — with no account of which layer paints over which; [`commands.md → Gesture activation`](../../commands.md#gesture-activation) explains the gesture zone and the trace without touching how they are composited. The individual constraints do exist as comments at each site, which is why each one was eventually fixed; what is written nowhere is that they are one failure mode.

The cost of missing it is not a wrong style, it is a wrong theory. #3791 was pursued as a layering problem in `TraceGesture` — the component that looked wrong — for six weeks and two rejected refactors of it, before the question became what the blur was nested inside.

## When to Apply

- **Before moving a blur, glow or overlay to a new parent,** walk every ancestor between it and the content it acts on and check for a stacking context. If one exists, the token is dead on arrival; move the layer out instead of raising its number.
- **Reproduce in the engine that fails.** Three of the four incidents were engine-specific, two of them on Android WebView, and none of them is visible in desktop Chrome.
- **Do not expect the e2e suite to catch a layering regression.** The `GestureMenu` snapshot in [`ui.ts`](../../../src/e2e/puppeteer/__tests__/ui.ts) hides `[data-testid=gesture-trace]` before capture, because the trace's canvas glow renders differently across environments — so the exact ordering #4466 fixed is excluded from the one artefact that would show it, and the run is headless Chromium with device emulation regardless. A manual check on a real device is the test.
- **Adding `will-change`?** Name the engine and the frame it drops in the comment, confirm the element unmounts so the layer is freed, and prefer an opt-in prop over a blanket style when the component has other callers.

## Examples

Approaches developed and abandoned on the way to the sibling arrangement:

| Tried | What happened |
| --- | --- |
| A `gestureMenuBlur` token just below `gestureTrace`, with the blur still inside `PopupBase` | Built and reverted inside #4466. A token cannot lift the trace above the blur while both are sealed in the `<View>`'s `z-index: 0` context — the revert is what turned the investigation from the ranks to the containers. |
| `createPortal` from `TraceGesture` to `<body>` | Rejected before it was built: the React tree would show the trace under `MultiGesture`'s `<View>` while the DOM had it under `<body>`. "I'd rather a more decoupled hierarchy than portals." |
| Extracting `TraceGesture` out of `MultiGesture` | Greenlit, attempted, abandoned. The two share the `eventNodeRef` that forwards touch events to the signature canvas; threading it up to `AppComponent` risked breaking gesture drawing and would not have fixed the blur, whose cause was its own nesting. #4466 landed with no such refactor. |
| Mounting the blur beside `<Content/>` in `AppComponent`, sized from `commands.length` × row height | Ordered correctly — `content` → `gestureContentBlur` → `gestureTrace` — but the blur no longer shared a box with the menu, so its height came from a formula over shared rem constants that menu changes would not carry into. Review moved `GestureMenu` into the `<View>` and made the blur a sibling of `PopupBase`; the formula was dropped for `position: fixed; inset: 0` with a `minBlur` floor. `CommandCenter.tsx` does compute a `blurHeight`, from the sheet's live height rather than a content count — the rule is which box a blur can size itself from, not a ban on measuring. |
| `will-change: transform` to force a compositing layer for a `mix-blend-mode` that no-oped in Safari (#3468) | Discussed in review on the Command Center Done button, never landed. The blend was removed rather than propped up: the button in `CommandCenter.tsx` is a plain `background: 'commandCenterDoneButton'`, and no `will-change` exists anywhere under `CommandCenter/`. |
