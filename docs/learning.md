# Learning Journey

The learning journey helps early users learn commands gradually through normal use. The full design is tracked in [#5481](https://github.com/cybersemics/em/issues/5481). A pinned command stays in a corner widget with a practice-progress ring; opening the ring reveals its gesture and a link to its Command Universe detail page.

## State

`state.learning` ([`LearningState`](../src/@types/LearningState.ts)) holds the pin, its practice record, and what the user has discovered and learned:

```ts
{
  pinnedCommandId: CommandId | null
  progress: Partial<Record<CommandId, { reps: number; targetReps: number }>>
  discovered: CommandId[]
  learned: CommandId[]
}
```

A command is in one of three states:

- **Undiscovered**: the user has no recorded deliberate encounter with it. The Gesture Menu does not list it.
- **Discovered**: it is in `discovered`. The user has revealed it in the Gesture Menu (see [Command Discovery](#command-discovery)), opened its Command Universe detail page, pinned it, or performed it by gesture or keyboard. `discovered` starts as `LEARNING_STARTER_COMMANDS` in [`constants.ts`](../src/constants.ts), so the Gesture Menu is never empty, and learning saved before discovery existed starts from the same list. [`isCommandDiscovered`](../src/selectors/isCommandDiscovered.ts) answers the question, and also counts Cancel and Command Universe, which the menu always lists, and every command while a test has stubbed the command list.
- **Learned**: it is in `learned`, because the user filled its practice ring. It stays learned after it is unpinned and its reps are erased, and it stays in `discovered`. Nothing reads `learned` yet, and using a command some number of times without pinning it does not learn it.

- Progress is keyed by stable `CommandId`, never by label, category, or position, so relabeling a command preserves its record.
- Progress exists only for the pinned command. A fresh record is created when a command is pinned, capturing the target from `LEARNING_TARGET_REPS` in [`constants.ts`](../src/constants.ts); unpinning, or pinning a different command, erases it. Changing that constant does not change the existing record.
- Reaching `targetReps` fills the ring, plays its flourish, and adds the command to `learned`.

[`storageModel`](../src/stores/storageModel.ts) saves the pin and progress under the `learning` key. [`initialState`](../src/util/initialState.ts) reads the saved state through that model, just like font size and jump history; no separate hydration action is needed. The decoder validates the stored structure and discards malformed progress records. The widget ignores a saved command that is no longer in the registry. Pinning, unpinning, and awarding a rep save the new learning state through `storageModel.set`. The pinned selection is intentionally device-specific. Practice progress stays local for now; synchronizing learning progress across the user’s devices is deferred. Here, device-local storage means this browser profile and app origin, not shared storage across installations.

## Actions

- [`pinCommand`](../src/actions/pinCommand.ts) — selects the command and starts a fresh progress record, erasing any other command's record. Pinning the already pinned command keeps its record. Pinning a different command closes the tooltip.
- [`unpinCommand`](../src/actions/unpinCommand.ts) — clears the selection and erases its reps, and closes the tooltip.
- [`showPinnedCommandTooltip`](../src/actions/showPinnedCommandTooltip.ts) — opens or closes the pinned command's tooltip. It does nothing when asked to open while no command is pinned.
- [`pinnedCommandAddRep`](../src/actions/pinnedCommandAddRep.ts) — adds one rep to the pinned command. The command runner dispatches it after a successful keyboard shortcut or gesture, and the action creator dispatches nothing unless the command is the current pin and has its progress record, so other commands add no Redux action. Reps keep counting past the target, and each rep at or past it plays the ring's flourish.

These actions are registered `undoable: false`, and `learning` is listed in `statePropertiesToOmit` in [`undoRedoEnhancer`](../src/redux-enhancers/undoRedoEnhancer.ts), so pinning and practice never add an undo step or get reverted by undoing an edit.

Whether the tooltip is open is UI state, not learning state, so it lives outside `state.learning`: the top-level `showPinnedCommandTooltip` flag sits beside `showSidebar` and the other `show*` flags. It starts false, is never persisted, and like them changes only through a non-undoable action. The pin reducers close it in the same update that changes the pin, the way `setCursor` closes the toolbar pickers, so the flag can never be true for a command that is no longer pinned. `PinnedCommand` also closes it when it unmounts, since a flag that outlived the widget would reopen the tooltip when a modal, such as one opened by the pinned command itself, closes again.

The command runner emits a success event once per top-level invocation, including a multicursor invocation. It does so as soon as `exec` returns, provided the command was executable, did not throw, and did not set a new app error. Asynchronous work the command starts is not awaited: performing the command where it can execute is the rep, whatever a server, the AI disclosure, or the clipboard later returns. A guard that should stop an invocation from earning a rep therefore belongs in `canExecute`, not in an early return from `exec`. Toolbar, Command Center, Command Universe, and internal calls do not earn reps or dispatch a practice action.

## Command Discovery

The Gesture Menu lists only discovered commands, and one undiscovered command as a **ghost**: a row whose gesture is drawn as usual but whose title is a fog the width of its name. Holding still on the ghost opens Command Discovery, a screen that introduces the command, instead of performing it.

**The ghost.** `useDiscoveredCommands` in [`GestureMenu`](../src/components/GestureMenu/GestureMenu.tsx) splits the commands that match the gesture into the discovered ones and the first undiscovered one, placed after them and before Cancel and Command Universe. An exact match sorts first, so when the gesture matches an undiscovered command exactly, that command is the ghost. The split is made in the menu rather than in `useFilteredCommands`, which still sees every command: it also feeds the segment haptics and Command Universe search. A chained command is never the ghost, and during the tutorial, which teaches by gesture, every command is listed. `GhostTitle` in [`GestureMenuItem`](../src/components/GestureMenu/GestureMenuItem.tsx) draws the name as fog ([`GhostFog`](../src/components/GestureMenu/GhostFog.tsx)): in an even tinted color, blurred until it cannot be read. The fog is even across the whole name, so before the user has done anything it never looks partly filled.

**The hold.** Once the gesture matches the ghost, the row's subtitle reads "hold to discover" in an italic, glowing treatment, and the menu's own background gives way, over 250 ms, to the picture Command Discovery plays over ([`DiscoveryBase`](../src/components/Learning/DiscoveryBase.tsx)): the app dimmed, and the discovery's light waiting above the screen with its foot lighting the top (`GhostBase`). Holding the finger still then charges the ghost ([`useGhostCharge`](../src/components/GestureMenu/useGhostCharge.ts)): a denser, brighter fog spreads across the title from the left, with a soft leading edge, thickening as it goes. The charge starts once the finger has rested for 150 ms, so a pause on the way to letting go never shows any, and fills over 1.5 s. Moving the finger drains it twice as fast. The finger counts as still while it stays within `TOUCH_SLOP` of where it settled, so the few pixels a resting finger always drifts do not drain it. Its position comes from [`gestureFingerStore`](../src/stores/gestureFingerStore.ts), which `MultiGesture` writes for the gesture's own finger, so a second finger cannot hold or drain the charge. A haptic ratchet clicks at each step of `GHOST_CHARGE_TICKS` on the way up, closer and closer together and each a little stronger and crisper than the last, and not while it drains. The charge is a MotionValue advanced on Motion's frame loop, and the maths of one frame is the pure [`ghostCharge`](../src/components/GestureMenu/ghostCharge.ts).

**Warming up the genie.** The genie performs the discovery, and starting it means downloading its code the first time and creating its WebGL context, long enough to stall whatever is animating then. So the ghost lets it out, invisible, as soon as the gesture matches it ([`useGenieWarmup`](../src/components/HelpGenie/useGenieWarmup.ts)), while little else moves, and puts it back if the user moves on without discovering.

**Discovering.** When the charge is full, `discoverFromGestureMenu` in [`commands.ts`](../src/commands.ts) dispatches `discoverCommand` and `commandDiscovery`, and closes the menu, while the finger is still down. The menu fades out over Command Discovery, and keeps showing the command as the ghost while it does, rather than redrawing it mid-fade as an ordinary row with its description. That finishes the gesture: `handleGestureEnd` returns early while Command Discovery is open, so the release that follows performs nothing, even though its command is now discovered. `MultiGesture` only consults `shouldCancelGesture` on touchstart and on moves, so without that return a finger lifted without moving would perform the command.

**The release.** Letting go before the charge is full cancels: `handleGestureEnd` performs nothing and discovers nothing when the Gesture Menu is open and the gesture matches an undiscovered command, and closes the menu, so a gesture that happens to match an undiscovered command is never performed by surprise. A gesture released before the menu opens is performed as usual, whether or not its command is discovered, and performing it discovers it. So is every gesture during the tutorial. `discoverCommand` dispatches only for a command that is not yet discovered, so performing a command the user already knows still adds no Redux action.

**The screen.** `state.commandDiscovery` holds the command being introduced, or null; it is UI state beside the `show*` flags, never saved. [`CommandDiscovery`](../src/components/Learning/CommandDiscovery.tsx), mounted beside `PinnedCommand`, plays the design made in EffectCraft ("Hold to discover - A pour"). Its times, positions, easings and paths are read out of that design, in [`discoveryDesign`](../src/components/Learning/discoveryDesign.ts) and [`discoveryTimeline`](../src/components/Learning/discoveryTimeline.ts). Its type is the Gesture Menu's, in rem so it follows the font size, so the command reads the same as it did in the menu a moment before. The name is a selected row's title, the description is the ghost's italic hint, and the note is a row's description. The help genie performs it. Times below are from the moment of discovery:

1. **The pour** (0–0.83 s). The screen is drawn on two layers. Beneath the closing Gesture Menu, on `commandDiscoveryBase`, is the same picture the menu faded into during the hold ([`DiscoveryBase`](../src/components/Learning/DiscoveryBase.tsx)): the app blurred and dimmed to 10%, and the light. So the menu's rows fade over an unchanged background, and only the light moves. The light is lamps shining on the screen from behind it ([`discoveryLight`](../src/components/Learning/discoveryLight.ts)), so it behaves like real light. A lamp lights a wall with a falloff that never reaches zero, so its light has no edge to see, and when it moves the whole screen's light shifts with it rather than a shape travelling. A key lamp is lowered with the command, on the fog's own descent, from the top of the screen to just below where the name comes to rest; a violet lamp to the upper left comes up and a dim mauve lamp to the right dims a little on the same curve, so the light moves exactly with the command. The lamps are fitted to the light while the user holds and once it has poured, in colors deeper than the design's, which looked pale in the app. The light changes so gently that it is calculated at 96 points across on a canvas stretched over the screen, redrawn only while the playhead moves, with a little noise to break up the banding eight bits would draw across so dark a gradient. Above the menu, on `commandDiscovery`, the fog the command was in, fully charged ([`GhostFog`](../src/components/GestureMenu/GhostFog.tsx), shared with the menu's ghost), falls over 833 ms from where the ghost's title was, with the command's gesture beside it, also from where it was in the menu, which the ghost row reports to [`commandDiscoveryStore`](../src/stores/commandDiscoveryStore.ts) as it lays out, to where the name will be: its row's center is at 38.3% of the screen's height, as in the design. As it lands, the fog thins to 86% and softens over the next 700 ms. Wherever the screen brings something into or out of focus (the fog softening, the name sharpening as the genie crosses it, the description developing) it fades between a sharp and a blurred copy ([`BlurCrossfade`](../src/components/Learning/BlurCrossfade.tsx)) rather than animating a blur, which WebKit re-renders unevenly: it snaps from blurred to sharp between two frames and leaves seams at the edges of the blurred box.
2. **The reveal** (from 0.93 s). The genie swoops in from off the left of the screen at 85% opacity and skims the fog. The fog clears behind its head, and the name appears there, sharpening from an 8px blur as the genie crosses it. A chevron appears after the name once the genie has passed its end. The genie then loops the loop past the end of the name.
3. **The description** (2.55–3.88 s). The genie orbits the description and the note beneath it once, and they develop as it goes round, brightening and sharpening from a 6px blur.
4. **Done** (3.87–4.27 s). The genie hovers above the description's right end while Done rises 10px into place: a glass pill, from the design's glass button texture: a faint blue wash that fades towards the bottom, edged by a hairline stroke that is blue-violet along the top and dark along the bottom.
5. **The landing** (4.82–5.82 s). As the genie dips, the ring and the hint beside it, "Drag the command here to pin it.", appear: an empty ring when no command is pinned, which shrinks into place from 125%. A pinned command's own ring is raised over the screen instead. The genie settles in the ring at 5.07 s and a ripple leaves it, growing to 180%. A genie that was only let out for the discovery fades into the ring and is put back; one that was already out stays.

The genie leaves glitter behind as it flies: 55 soft specks, each dropped where the genie's head is at its time in the design, which drift to where they settle, then wander and twinkle while they fade to a glow (`GLITTER`). Once settled, each wanders slowly, on a loop of ten to twenty seconds, made of two waves at unrelated speeds so it never traces a visible circle. They run on their own clock rather than the playhead, so they keep drifting and twinkling for as long as the screen is open.

Everything on the screen is derived from one playhead, a MotionValue that runs from 0 to the end of the timeline, rather than from a delay per part, so the parts stay in step however the frames fall. The genie's route ([`discoveryRoute`](../src/components/Learning/discoveryRoute.ts)) is the design's flight (`GENIE_PATH`) moved onto the real screen. Each point is placed against what the genie is over at that moment: the name, the description, or the ring. Inside one of those it is stretched in proportion; outside, it keeps its distance from the nearer edge. The flight therefore fits any name, description and screen, and is the design's flight wherever they match it. The screen measures those once it has laid out. Each frame it steers the genie through a [performance](#performances), on a stiff spring that does not overshoot, so the genie follows the design's flight closely. It reveals the name as far as the genie's head has actually reached, which the genie reports back; while the genie cannot draw, the reveal follows the route instead.

Haptics mark each beat ([`discoveryHaptics`](../src/components/Learning/discoveryHaptics.ts)): a heavy hit with a short fading rumble on discovery, a dull thud as the fog settles, a crisp tap as the genie finishes revealing the name, and two rising taps as it lands. Under them, a quiet, soft hum follows the genie's speed for the whole flight, swelling as it speeds up and fading at the hover. A playing pattern cannot be changed, so the hum is worked out when the flight starts: [`flightSpeeds`](../src/components/HelpGenie/flightSpeeds.ts) flies the route on the same spring the genie flies it on, which is solved exactly and so matches the genie on screen, and the speeds become the strength curve of one continuous event, cut to the 16 control points Core Haptics allows on a curve. They are written in Apple's AHAP format and played through `@capawesome/capacitor-haptics`, which plays custom patterns with Core Haptics on iOS; `haptics.pattern` in [`util/haptics`](../src/util/haptics.ts) converts them ([`ahap`](../src/util/ahap.ts)).

The app does not scroll behind the screen (`useLockBodyScroll`), and a swipe on the screen scrolls nothing. Done or Escape closes it at any point. Done cannot be pressed before it appears. The screen shares the ring's dock position ([`pinnedCommandDock`](../src/components/Learning/pinnedCommandDock.ts)) to find where the genie lands. `shouldCancelGesture` cancels any trace while the screen is shown.

**Starting over.** Settings has "Reset discovered commands", which dispatches [`resetDiscoveredCommands`](../src/actions/resetDiscoveredCommands.ts). It returns `discovered` to the starter commands and the pinned command, if any, so the rest can be discovered again, and saves the change. Practice progress is kept.

## Pinning from the Command Universe

Every command's detail page ([`CommandUniverseDetailPage`](../src/components/CommandUniverse/CommandUniverseDetailPage.tsx)) has a Pin Command row after the command description and gesture, separated by a divider. It reads Unpin Command when that command is the pinned one, and its description names the command that pinning would replace. Pressing it never executes the command.

## The corner widget

[`PinnedCommand`](../src/components/Learning/PinnedCommand.tsx) is mounted in `AppComponent` inside `MultiGestureIfTouch` and renders nothing while no command is pinned. The ring is fixed to the screen corner at the NavBar's bottom safe-area offset, so it stays put however the page scrolls, and sits over the footer links at the end of the page rather than riding the NavBar up when the footer enters. It renders in place rather than through a portal: nothing above it in `AppComponent` creates a stacking context. It is on the `pinnedCommand` z-index layer just above `navbar`, and while the overlay is open or fading out it rises to the `pinnedCommandExpanded` layer, above popups and dialogs and below only the help genie and Show Touches, which ignore pointer events. The tooltip's surface shares that layer and renders first, so the ring paints over it. The ring also stays on `pinnedCommandExpanded` while the Mobile Command Universe is open, so the command the user has just pinned stays in view and tappable over the dialog. Under the Sidebar, the Command Center, and other overlays it stays docked beneath. `PinnedCommand` wraps the ring and tooltip in an element marked `data-above-dialog`, which [`Dialog`](../src/components/dialog/Dialog.tsx) reads as a press that is not outside it, so tapping either leaves the Command Universe open. Position lives on that fixed element, and scale and lift on the button inside it. As it scales, the ring also rises so its center meets the center of the tooltip's row of genie and text. [`useRingExpansion`](../src/components/Learning/useRingExpansion.ts) measures that rise: when the tooltip opens, and on resize while it is open, it reads where the ring's fixed dock and the row are on screen, and from the same read how far the enlarged ring reaches in from the right edge of the screen, which the row reserves as right padding, less the surface's own side padding, so its text stays clear of the ring. The ring's visible center and left edge within its box come from [`ringGeometry`](../src/components/Learning/ringGeometry.ts). This is one layout read per opening, taken instead of restating the tooltip's padding, row height, and safe-area inset in a CSS expression that had to be kept in step with the tooltip by hand. The ring's scale and rise follow the surface's eased visibility, so they open and close together with it, and the ring stays on the raised layer for as long as the surface is visible at all, through its exit fade. Only the ring button accepts pointer events, leaving the surrounding corner open to gestures and taps. The button's hit area is its 73px box extended 16px upward and 12px leftward through a pseudo-element, since the ring fills only the middle 44px of the box and the box already reaches the right edge and the floor; the pseudo-element leaves the box itself, and so the ring's placement and scale origin, unchanged. Tapping the ring opens the tooltip, and tapping it again closes it; holding it for `TIMEOUT_LONG_PRESS_THOUGHT` plays a light haptic and opens the command's Command Universe detail page instead, the same as the tooltip's command-name link, and the platform's long-press menu is suppressed. Neither the ring nor the tooltip is text-selectable. Each awarded rep also plays the command's icon animation inside the ring, through [`PinnedCommandIcon`](../src/components/Learning/PinnedCommandIcon.tsx), the same Lottie animation the toolbar plays on activation, and like the toolbar it skips a toggle command that has just been switched off. The button is named `Show gesture for <label>`, describes the current rep count and captured target, and reports whether its tooltip is expanded.

While a command is pinned, the NavBar's inner row leaves `PINNED_COMMAND_RESERVED_WIDTH` free on the right so breadcrumbs and buttons do not run under the ring or its extended tap target. The NavBar's full-width blackout is untouched, so no gap opens behind the bottom chrome.

## The ring

[`PinnedCommandRing`](../src/components/Learning/PinnedCommandRing.tsx) draws a 73×73 box using values derived directly from the original design in Figma:

- **Track**: a stroked SVG circle with the original design's linear gradient, layer blur, drop shadow, 52% opacity, and `mix-blend-mode: hard-light`.
- **Fill**: in Figma the arc is an annular sector with an along-arc gradient and an *angular progressive layer blur* (tail 14 → head 4, Figma units; a Figma blur value is 2σ). No browser has an angular blur, so the arc is one `conic-gradient` (color and progress angle together) masked to the annulus, stacked five times; each copy is masked to an angular band that crossfades into its neighbours and is wrapped in a div with a different `filter: blur()`. The blur sits on the wrapper so it applies after the inner masks and softens the ring edges. Each rep animates the progress angle over `durations.medium`, starting from the currently visible angle if another rep arrives mid-animation. Mounting a ring, switching pinned commands, and reduced-motion preference render the current angle immediately.
- **Color and flourish**: the fill is mono at rest, including when full. Opening the tooltip reveals the colorful fill in step with the same eased visibility that drives the glow and ring scale; closing it returns the fill to mono. A dry run over the Command Universe plays a separate burst instead (see below). Each rep the current pin earns at or past its target plays a flourish driven by one eased timeline over `durations.slow`: the whole arc spins once, its color rises to the colorful stops at the half turn and falls back to mono by the end, and any fill still short of full closes during the first half of the turn, so the completing rep flows straight into the celebration instead of finishing its own fill first. The colorful layers are mounted while the tooltip is visible or a flourish is playing, and either one can keep them visible when the other fades. `PinnedCommand` counts those reps per pin and passes the count as the ring's `flourish` prop; the ring plays on each change and never on mount, so progress loaded from storage or shown after repinning does not celebrate. Reduced-motion preference keeps the color pulse and skips the spin.

The component is organized into same-file visual layers: `RingTrack` owns the stationary SVG and its unique filter IDs; `RingProgress` draws the fill and combines the flourish's color pulse with the tooltip's color, taking whichever is stronger, while [`useRingFill`](../src/components/Learning/useRingFill.ts) tweens the fill and [`useRingFlourish`](../src/components/Learning/useRingFlourish.ts) plays the flourish and closes the fill while it does; `BlurredProgressArc` builds the gradient and delegates each mask/blur pair to `RingBlurBand`; `RingIcon` centers the command icon. These component boundaries add no DOM wrappers. `RingProgress` remains mounted at zero progress so its animation state survives changes to the visible fill.

[`TestPinnedCommandRing`](../src/components/modals/TestPinnedCommandRing.tsx) renders the ring at 0%, 30%, the export's 63.5%, 90%, 100% mono, and 100% colorful for the [`pinned-command-ring`](../src/e2e/puppeteer/__tests__/pinned-command-ring.ts) snapshot. The colorful state supplies a fixed color opacity of 1, independently of tooltip interactions or a running flourish. This test uses `screenshot({ preserveFilters: true })`, so the snapshot covers geometry, gradients, blur, and shadows.

## Gesture tooltip

[`PinnedCommandTooltip`](../src/components/Learning/PinnedCommandTooltip.tsx) uses the shared [`NotificationSurface`](../src/components/Notifications/NotificationSurface.tsx), so it sits where [`Tip`](../src/components/Notifications/Tip.tsx) does, blurs the content beneath it the same way, and fades the same way; unlike Tip it does not swipe to dismiss, since a swipe over it is a gesture trace. At the bottom-right anchor that blur and its scrim are a corner rather than a full-width band: a box sized to the content and feathered by one shared elliptical mask, so on a landscape phone the rest of the thoughtspace stays sharp. Its visibility animation uses the Sidebar's gentle open curve and the Command Center's gentle-start close curve. The ring's scale and color follow that same eased opacity. It differs from Tip in three ways:

- **Glow.** The surface's `pinnedCommand` glow variant paints `public/img/pinned-command/pinned-command-glow.avif` with extents that do not follow the content height, unlike Tip's. Portrait and landscape are keyed by the `lg` breakpoint in [`notification.ts`](../src/recipes/notification.ts), which is where the tooltip's anchor switches. The glow element is the image's own footprint: the image's constants live in its aspect ratio, and every other value is a fraction of one viewport dimension. Portrait scales with viewport width and anchors left, matched to the design at 412×922; landscape scales with viewport height and anchors right, matched at 922×412, with a heavier blur. Sizing from a single dimension avoids iOS Safari's unstable `vh` in portrait, and the bottom anchor adds the safe-area inset so the bright band follows the text above the home indicator. Tablet and desktop share the landscape branch, where the glow must stay localized in the corner at the phone size, so each height-relative value there is capped at its value on a 412px-tall viewport. The tooltip passes the surface glow to `NotificationSurface` as `glowClassName`, a class that sets the glow's background image, so the image is in the CSS and is preloaded with the app's other background images; Tip does the same for its rainbow glow, so each image path sits beside the component that shows it. Static rainbow-glow placement is defined directly in the anchor styles. Motion supplies the ring’s animated transform directly through `useMotionTemplate`, with `useBreakpoint` selecting the responsive bottom padding; no feature-specific animation variables are needed. Notification easing is defined in `constants.ts`. The corner's blur and scrim share one feather, the `--notification-blur-feather` variable that the notification recipe sets at the bottom-right anchor.
- **Content.** A row of the learning genie button, which lets the [help genie](#help-genie) out or puts it back, the command's name as a button with a chevron that opens its Command Universe detail page directly, and one line saying how to activate it: trace the gesture on touch devices, press the shortcut otherwise, or open the Command Universe when the command has neither. Over the Command Universe, where a trace is only practice, the touch line reads "Trace the gesture to practice." instead; shortcuts do not run there, so the shortcut line asks the user to close Commands first. Text is left-aligned at both anchors. The genie and the text form one vertically centered row so they read as a unit with the ring in the corner, built from same-file parts named for what they show (`PinnedCommandGestureDiagram`, `LearningGenieButton`, `PinnedCommandTooltipTitle`, `PinnedCommandTooltipSubtitle`, and `ClearButton`); Clear hangs below that row, outside its flow and in the surface's bottom padding, so it does not pull the row's center down. That padding is tight on devices without a safe-area inset, so the tooltip adds bottom padding that shrinks as the inset grows.

- **Diagram.** Below `lg`, when the command has a gesture, its canonical gesture from the command registry is drawn large above the text with the Command Universe detail page's diagram styling. Behind it is its own glow, `public/img/pinned-command/pinned-command-gesture-glow.avif`, positioned and sized relative to the diagram box so the two stay aligned on every device; it is separate from the surface glow because the diagram can be absent. There is no landscape design for the diagram yet.

The tooltip is built to be practiced on. Except over the Command Universe, where a press that fell through would land on the dialog's backdrop and close it, it passes `pointerEventsPassThrough` to the surface, which makes the content layer ignore pointer events so a trace that starts over the diagram reaches the thoughtspace and can activate the command; only the text row opts back in. While a gesture is in progress, read from the gesture store's current sequence, the surface's blur, scrim, and glow and the tooltip's text row fade to half opacity through the surface's `dimmed` prop and the row's opacity transition, and the diagram stays fully visible so it can be traced over. The gesture menu does not open while the tooltip is open: `handleGestureSegment` reads the `showPinnedCommandTooltip` flag from Redux. The tooltip closes when the user taps Clear, presses Escape, taps the ring again, or taps outside the tooltip and the ring, which the tooltip receives by ref, and when a rep lands while it is open. Because pointer events pass through, a press that starts a trace looks like a tap when it goes down, so the tooltip does not classify presses itself: it waits for a press to end and asks what `MultiGesture` made of it. A press during which the gesture store recorded a gesture was a trace and leaves the tooltip open; a press the browser cancels was taken over as a scroll and also leaves it open; any other press that ends outside the tooltip and the ring was a tap and closes it. Opening it or following its command-name link does not execute the command or award practice reps.

The ring records the editor's selection offsets before pointer activation can move focus, except over the Command Universe, which took that snapshot when it opened and has since cleared the selection. When the command-name button opens the Command Universe, its open action preserves that snapshot rather than replacing it with the selection inside the tooltip. This lets commands that act on selected text continue to use the editor range.

### Dry run over the Command Universe

Over the Mobile Command Universe the tooltip can be traced on, as a dry run: the mechanics of tracing the gesture without executing anything. `PinnedCommand` is mounted inside [`MultiGesture`](../src/components/MultiGesture.tsx), whose responder only sees touches on its own descendants, so while the Command Universe covers the thoughtspace the only touches that can become a gesture are those on the pinned command. `shouldCancelGesture` normally abandons every gesture while the Command Universe is open; it lets one through when the tooltip is open and the touch started on the pinned command (`data-above-dialog`), so the Command Universe itself still scrolls. The trace is drawn there too: `TraceGesture` stays mounted over the Command Universe while the tooltip is open, and the `gestureTrace` layer sits above dialogs and below `pinnedCommandExpanded`, so it draws over the Command Universe and under the tooltip, as it does over the thoughtspace. The gesture menu uses its own `gestureMenu` layer above `gestureTrace`, preserving the order of menu, sharp trace, and `gestureContentBlur` over the thoughtspace. Its content blur stays a sibling of the menu's `PopupBase` so the blur does not rise into the menu's stacking context. Segment haptics run, and the gesture menu stays closed as it does for any trace over the open tooltip.

When the trace ends, `handleGestureEnd` executes nothing and awards no rep. If the user drew one of the pinned command's own gestures exactly, looked up in `commandGestureIndex` so that a chained gesture ending in it does not count, it triggers `pinnedGestureDryRun` on [`commandEmitter`](../src/stores/commandEmitter.ts), which carries one-off signals about commands that change no state, and the ring plays its burst: since the ring is how success is shown, it celebrates there too, but without filling. A colorful ring with no tail or head, drawn as one blurred annulus, starts just outside the ring, grows away from it to 1.6× over `durations.slow`, and fades as it grows, so it never rests on the ring where it could read as a full fill. The fill, its color, and the rep count are untouched, and the ring's own flourish is not played, since it ends with the ring drawn full. Reduced-motion preference keeps the fade and skips the growth. The tooltip stays open so the user can trace again.

The [`pinned-command-tooltip`](../src/e2e/puppeteer/__tests__/pinned-command-tooltip.ts) snapshots pin Context View, open its tooltip from the ring, hide the HUD, and guard the layout at a portrait and a landscape viewport, so they cover the expanded ring's real footprint beside the text. The screenshot helper disables CSS filters, so the snapshots cover placement and extents, not the blur.


## Help genie

The help genie is a glowing orb with a tapering, sparkling trail that flies over the app. It follows the pointer or a finger, can be sent to a point from code, and performs in [Command Discovery](#command-discovery).

### State

`state.helpGenie` ([`HelpGenieState`](../src/@types/HelpGenieState.ts)) holds what the app wants from the genie, not its motion:

```ts
{
  visible: boolean
  target: { x: number; y: number } | null
  unavailable: boolean
}
```

- [`toggleHelpGenie`](../src/actions/toggleHelpGenie.ts) lets it out and puts it back, or sets it with `value`. The genie buttons dispatch it: Help in the Command Universe header ([`DialogHeader`](../src/components/dialog/DialogHeader.tsx)) and the learning genie button in the pinned command tooltip. Both report the state through `aria-pressed`.
- [`moveHelpGenie`](../src/actions/moveHelpGenie.ts) sends it to a point in the viewport, in CSS pixels. It flies there with its full effect. It still follows the pointer too; whichever moved last is where it goes.
- [`disableHelpGenie`](../src/actions/disableHelpGenie.ts) marks it unable to run on this device and puts it away. Its buttons are disabled while `unavailable` is set.

None of this is saved, so a reload puts the genie away and clears `unavailable`. The actions are registered `undoable: false`, and `helpGenie` is listed in `statePropertiesToOmit` in [`undoRedoEnhancer`](../src/redux-enhancers/undoRedoEnhancer.ts), so undoing an edit never moves or hides the genie. Its moment-to-moment motion is not in Redux: it changes every frame and lives in the animation.

### Overlay

[`HelpGenie`](../src/components/HelpGenie/HelpGenie.tsx) is mounted at the end of `AppComponent`, outside the modal condition, so the genie keeps flying over dialogs and modals. It covers the viewport on the `helpGenie` z-index layer, the highest, above `dialog`, and ignores pointer events, so it never blocks a tap or a gesture. It screen-blends with the app, so the genie only ever adds light to what is beneath it. The blend is on the overlay rather than the canvas because the overlay is a stacking context: a blend inside it would only mix with the empty overlay.

The genie needs WebGL. `HelpGenie` checks for it before loading the canvas, and loads the canvas lazily, so Pixi is only downloaded the first time the genie is let out, never by a device without WebGL, and never by the JSDOM tests. If the genie cannot start (no WebGL, its code fails to download, Pixi starts without WebGL, or it throws while running), it dispatches `disableHelpGenie` and logs why.

### How it works

The genie is drawn with [PixiJS](https://pixijs.com/) through `@pixi/react`, in [`components/HelpGenie`](../src/components/HelpGenie). Each frame runs the same pipeline:

1. **Input.** The target is the pointer, or wherever `moveHelpGenie` last sent it, or during a [performance](#performances) the performance's target.
2. **Step.** [`stepGenie`](../src/components/HelpGenie/stepGenie.ts) turns the last [`GenieFrame`](../src/components/HelpGenie/GenieFrame.ts) into the next. The head moves towards the target on a spring ([`genieMotion`](../src/components/HelpGenie/genieMotion.ts)) and remembers its new position; the positions from the last `MEMORY` ms are the trail, so it grows with speed and shrinks into the head at rest. Sparkles are born along the stretch just flown and old ones expire ([`sparkles`](../src/components/HelpGenie/sparkles/sparkles.ts)). The spring is solved exactly rather than stepped, so the genie flies the same path at 60Hz and 120Hz. `stepGenie` is pure, which is what makes the genie testable and a flight scriptable.
3. **Draw.** Three layers each draw that frame and keep no state of their own:
   - [`GenieHalo`](../src/components/HelpGenie/halo/GenieHalo.tsx) — the broad glow. [`haloShape`](../src/components/HelpGenie/halo/haloShape.ts) places its center slightly behind the head and lays points along the path either side of it; [`halo.frag`](../src/components/HelpGenie/halo/halo.frag) colors each pixel from its distance to those points. On a straight path the glow is an ellipse; on a turn it bends with the path, and cannot fold however tight the turn.
   - [`GenieTrail`](../src/components/HelpGenie/trail/GenieTrail.tsx) — a ribbon along the smoothed path ([`flightPath`](../src/components/HelpGenie/trail/flightPath.ts)), full width through a short neck and tapering to nothing ([`trailWidth`](../src/components/HelpGenie/trail/trailWidth.ts)), with a near-white hot core down its front. Blurred and screen-blended.
   - [`GenieSparkles`](../src/components/HelpGenie/sparkles/GenieSparkles.tsx) — each sparkle's position and fade at the frame's time, drawn in one batch. Color-dodged, so they only show where the genie is lit.

[`GenieCanvas`](../src/components/HelpGenie/GenieCanvas.tsx) owns the Pixi canvas and runs the pipeline. [help-genie.md](help-genie.md) has diagrams of how the modules fit together. Every tuned value is in [`constants.ts`](../src/components/HelpGenie/constants.ts), grouped by the part of the genie it shapes. Each layer creates its Pixi resources and destroys them when it unmounts. The canvas renders at the screen’s pixel density capped at 1.5×, reducing pixel work on high-density screens to leave headroom for the rest of the app.

The folder is laid out by part of the genie rather than by em's usual convention of types in `@types/` and pure code in `util/`, so each part's maths and drawing sit together.

### Performances

A performance is the genie flying where the app tells it, frame by frame, instead of following the pointer. [`geniePerformanceStore`](../src/components/HelpGenie/geniePerformanceStore.ts) is the channel between the performer and the genie: the performer writes a target each frame from its own playhead, and may write a spring to chase it on, such as a critically damped one for a landing that must not overshoot (`stepGenie` takes it in place of the genie's own). `GenieLoop` reads them at the start of its frame, and writes back where the head is, so the performer can act on where the genie actually is rather than where it was told to be. `startPerformance` begins one at a point; the genie notices the new performance and starts at rest there rather than flying in from wherever it was, including when the performance is what let it out. `endPerformance` hands it back to the pointer, and it stays where it left off until the pointer next moves. `genieOpacity`, a MotionValue on the `HelpGenie` overlay, fades it in and out. These are outside Redux because they change every frame. `warm` marks a genie let out only to be ready for a performance (`useGenieWarmup`); the performer that takes it over puts it back afterwards, as if it had not been out. Command Discovery is the only performer so far.
