# Documentation Strategy

How documentation for agents is organized in this repository, why, and how that compares with the approach Compound Engineering takes. This page records the research behind the current strategy so that the reasoning survives the people who did it. It was written in September 2026 after reading the Compound Engineering plugin source, this repository's own agent instructions and skills, and the formal and practitioner literature on documentation for coding agents.

The **Recommendations** section at the end is a set of proposals, not adopted policy. When one is adopted it belongs in [`AGENTS.md`](../../AGENTS.md) or the [`docs-sync`](skills.md#docs-sync) skill, and this page keeps the reasoning behind it.

## Summary

- **em** maintains comprehensive subsystem documentation under `docs/`, read on demand and required reading at plan time. Compound Engineering (CE) keeps a store of _learnings_ — one solved problem per file, written only when the reasoning is not recoverable from the final code — and re-derives everything else from the tree on every plan.
- The two approaches answer different questions. em's docs are a **map**: how a subsystem works now, with the reasoning folded in beside the mechanism. CE's learnings are **lessons**: what was learned the hard way, organized by problem type. CE does not argue against maps — its own repository carries a 5,249-word always-on `AGENTS.md`, 11,799 words of subsystem specs, and a 6,109-word glossary. Its bar governs only what enters the learnings store.
- The evidence splits documentation into three kinds with different answers. **Standing instructions** should be small and limited to what an agent cannot infer, with the reason attached. **Maps and overviews** have no measured benefit for navigation in any study, and code-element references are the part of documentation that measurably rots. **Lessons and rationale** are the highest-value content: rationale is the hardest thing to recover from code, failure-derived lessons are what transfers between sessions, and rules with recorded reasons are followed more and pruned more safely.
- em already does most of what the evidence recommends. Its always-on file is small. Its docs load on demand behind a named trigger. It repairs docs in the same commit as the code, and the measured drift rate of cited source paths (1.2%) is a third of the published baseline for open-source projects (3.9%). Its subsystem docs already hold lessons with provenance — `testing.md` cites 51 issues and pull requests, `cursor-and-caret.md` 38.
- Two things are exposed. There is no stated bar for what earns a paragraph, so the docs can only grow. And the largest required read, `testing.md`, costs about 26,000 tokens per test-writing session, a third of it a section about CI workflows that has nothing to do with writing a test.
- **Conclusion: keep the map, adopt CE's bar and its capture of failed approaches inside the existing docs, and add a routing layer to the largest doc.** A separate learnings store is not recommended now: em lacks the retrieval step CE built for its store, and CE's own history shows a store is invisible to any agent that does not know to search it.

## 1. The two approaches, from source

### 1.1 Compound Engineering's learnings store

Read from the installed plugin, `compound-engineering` 3.27.0 (released 2026-09-19, the newest release at the time of writing). The relevant skills are `ce-compound`, which writes learnings, `ce-compound-refresh`, which audits them, and the readers: `ce-plan`, `ce-ideate`, `ce-pov`, `ce-explain` and `ce-optimize` all search the store before they work.

**What a learning is.** One solved, verified problem, written as one markdown file under `docs/solutions/<category>/<slug>.md` with YAML frontmatter (`module`, `component`, `problem_type`, `severity`, `tags`, and for bugs `symptoms`, `root_cause`, `resolution_type`; for guidance `applies_when`). A bug-track learning has the sections Problem, Symptoms, What Didn't Work, Solution, Why This Works, Prevention. A knowledge-track learning has Context, Guidance, Why This Matters, When to Apply, Examples. The category directories are organized by _problem type_ (`runtime-errors/`, `test-failures/`, `architecture-patterns/`, `conventions/`, …), not by subsystem.

**The bar.** The gate that decides whether anything is written is quoted verbatim in `ce-compound`, `ce-compound-refresh` and the guide:

> A learning earns its place only when it holds durable project reasoning that is not readily recoverable from the final code, tests, types, comments, or existing documentation, and losing it would plausibly cause recurrence, material risk, or substantial rediscovery. Apply this counterfactual: if the learning document disappeared, would a future engineer reading the final implementation still be likely to repeat the mistake or redo substantial investigation? Completion, effort, and diff size do not establish eligibility.

The guide adds a placement table: machine-enforceable behaviour goes in a test, type or assertion; local rationale in a code comment; change-specific history in the commit or pull request; shared domain language in `CONCEPTS.md`; and only "durable reasoning that crosses implementation boundaries" in `docs/solutions/`. The stated motivation is loss: "The anti-patterns disappear first. What did not work was the most expensive part of the investigation, and it never gets written down."

**How it is retrieved.** `ce-plan` dispatches a `learnings-researcher` subagent at plan time. It reads `CONCEPTS.md` for vocabulary, greps `docs/solutions/` frontmatter fields (`title`, `tags`, `module`, `component`, `applies_when`) for keywords from the task, reads the first 30 lines of candidates, and fully reads only strong matches, returning constraints and "known failed approaches to avoid" as planning inputs. Discoverability is enforced: every `ce-compound` run checks that `AGENTS.md` mentions the store, in _informational_ rather than imperative wording, because "imperatives cause redundant reads when a workflow already searches". That check exists because of a failure: the plugin's own pull request #456 records that "only plugin-mediated workflows … know to search there".

**How it is maintained.** `ce-compound-refresh` classifies every learning as Keep, Update, Consolidate, Replace or Delete against the current tree. Its optional "worth lens" applies the bar retroactively and deletes a learning whose every claim is now stated by a named in-repo artifact — but only with positive evidence: "Topical overlap is not coverage; verify the specific reasoning is present and quote it." Before a learning is written, a script checks that cited paths and SHAs exist, and a validator subagent quotes the defining source line behind each behavioural claim.

**What CE does not say.** The durable bar governs the _learnings store_. It is not a claim that a project should have no other documentation. CE's own repository carries an always-loaded `AGENTS.md` of 5,249 words, a 6,109-word `CONCEPTS.md`, 11,799 words of subsystem-shaped `docs/specs/` describing each target platform's actual behaviour ("Verified 2026-08-21"), a `docs/development.md`, user guides, and 63 learnings totalling 63,210 words. One of those learnings, `developer-experience/always-on-agents-md.md`, records the opposite lesson to comprehensiveness: they moved essays out of the always-on file into task-loaded notes after an OpenAI note argued that "a stack of docs before every edit burns context, and extra test-cheerleading causes extra tests". CE also has `ce-explain`, which produces a grounded explanation of how something works _on demand_ and archives it only if asked. In other words, CE's answer to "how does this subsystem work" is to re-derive it at plan time — `ce-plan` runs a `repo-research-analyst` subagent over the tree on every plan — rather than to maintain it.

### 1.2 em's comprehensive docs

**What it is.** Thirteen subsystem documents under `docs/` and six under `docs/agents/`, 69,096 words in total, roughly 92,000 tokens. They were imported from the GitHub wiki in May 2026 ([#4223](https://github.com/cybersemics/em/pull/4223), following discussion [#4190](https://github.com/cybersemics/em/discussions/4190)) after an AI staleness pass, on the hypothesis that "even plugging in the docs we already have could meaningfully improve agent performance" — specifically against the observed failure of agents "reinventing existing infrastructure". Two design decisions from that pull request still shape everything: the docs are _grep-able_ ("agents already use `grep` to search the codebase"), and the glossary exists so that a grep for a term returns a definition and a link alongside code hits.

**What loads when.** The always-on surface is small: `AGENTS.md`/`CLAUDE.md` is 631 words. Copilot additionally auto-loads `copilot-instructions.md` (2,013 words) and the two instruction files (1,090 and 743 words). Everything else is on demand, but _required_ on demand: the [`plan`](skills.md#plan) skill makes `docs/readme.md`, `folder-structure.md` and `glossary.md` mandatory reading and requires quoting the relevant subsystem doc's constraint in the plan; `testing.instructions.md` requires reading `docs/testing.md` "in full" before writing tests, which is 19,467 words, about 26,000 tokens.

**How it is maintained.** [`docs-sync`](skills.md#docs-sync) runs as step 1 of [`end-session`](skills.md#end-session). It routes changed files to documents three ways (the plan's own list, a grep of `docs/` for changed identifiers, and a path-keyed table), and its editing rule is the one that most distinguishes em from CE: "Documentation describes how the project works now, and why it is that way. It is not a changelog." Reasoning must survive edits ("deleting rationale damages a doc as much as leaving a false claim in it"), and a change that contradicts recorded design intent is escalated rather than silently rewritten.

**Measured.** Since `docs/` was created, `main` has taken 844 commits. 431 touched `src/`; 143 of those, one in three, also edited a subsystem doc in the same commit. `docs/testing.md` has been edited in 77 commits, `commands.md` in 61, `cursor-and-caret.md` in 34. Of 332 distinct source paths cited across the docs, 4 no longer exist (1.2%), plus one deliberate placeholder. Drift exists, then, but at a low rate, and the co-change rate shows the same-commit rule is actually followed.

**What the docs contain.** The premise that em's docs "reproduce knowledge that can be inferred from the code or tests" is true of some documents and not of others. `folder-structure.md`, `glossary.md` and `data-model.md` are almost pure map: `data-model.md` cites 70 source paths and carries 9 sentences of rationale. But `testing.md` carries 103 rationale markers and 51 issue or pull request references; `cursor-and-caret.md` carries 33 and 38. Those references are learnings with provenance, written inline beside the mechanism they constrain. Three doc hunks from the last ten days of `main` show the shape:

- Toolbar dropdown taps (#5612): "Each option therefore applies on `touchend` and calls `preventDefault()` there. `touchstart` is not an alternative: React registers it passively, so `preventDefault()` in an `onTouchStart` is a no-op and the browser completes the tap regardless."
- Note focus (#5546): why `onFocus` bails when the app placed the caret, and why the `setCursor` it would otherwise dispatch is an undoable navigation action that would clear the offset mid-effect.
- Waiting in tests (#4045, in `testing.md`): a poll that "could never terminate" because `HOME_TOKEN` is not `'__ROOT__'`, recorded as the reason a rule exists.

Each of these passes CE's counterfactual: a future engineer reading the final code would plausibly repeat the mistake. em already captures durable reasoning. It captures it in the subsystem narrative rather than in an incident file, and the `docs-sync` rule "keep the reasoning" is what protects it. What em does _not_ do is state a bar for what earns a paragraph, or give a lesson a home when no subsystem doc covers its area — `docs-sync` explicitly tells the agent not to invent a document mid-session and to report the gap instead.

## 2. What the evidence says

The literature does not answer "comprehensive or minimal". It separates documentation into kinds, and the answer is different for each. Sources are listed at the end; several were read through abstracts, mirrors or search excerpts because the session's network policy blocked the primary hosts, and are marked as such there.

### 2.1 Standing instructions: small, non-inferable, with the reason attached

The strongest controlled result is Gloaguen et al. (ETH Zurich, February 2026), which ran four agent and model pairs on SWE-bench Lite and on 138 tasks from twelve repositories that had committed `AGENTS.md` files. Developer-written files raised resolution rates by 4% on average but cost up to 19% more per task; agent-generated files lowered them in five of eight settings and cost 20 to 23% more. The agents did read the files — a named tool was used 30 to 160 times more often when the file mentioned it — so the cost came from compliance, not neglect. The authors' recommendation is to "include only minimal requirements (e.g., specific tooling to use with this repository)". Anthropic's own Claude Code documentation says the same: target under 200 lines, "keep it to facts Claude should hold in every session", and cut "anything Claude can figure out by reading code", "file-by-file descriptions of the codebase" and "long explanations or tutorials". A survey of 100 popular repositories (dos Santos et al., June 2026) found that 62 restated rules a linter already enforced and 42 were bloated; 91 had at least one such smell.

Two results explain _why_ small files stay small. Chakrabarti (August 2026) tracked 247,694 instruction lifetimes across 1,867 repositories: agent instruction files grow by 4.9 net instructions per commit and more than triple over their lifetime, because appending is cheap and an instruction whose rationale is lost can never be safely deleted. Attaching an explanatory comment to each instruction cut excess growth from 211% to 1.4% and improved instruction-following by up to 23%. And Huang et al. (Harness-IF, August 2026) found that an instruction in the project file outranks the same instruction in a skill or tool description when they conflict — the always-on file is the highest-precedence surface, which is a reason to keep only what must win.

Within the range of file sizes most projects use, size and position do not seem to matter: McMillan (May 2026) varied file size from 25 to 500 lines, instruction position, and single versus nested files across 1,650 Claude Code sessions and found no detectable effect on adherence. Adherence decayed _within_ a session instead. Practitioner reports that "Claude ignores my file past 80 lines" may be measuring session length, not file length.

### 2.2 Maps and overviews: no measured benefit, and the part that rots

Gloaguen et al. also measured what a repository overview does. Eight of twelve developer-written files and essentially every generated one contained an architecture overview, and none of them reduced the number of steps an agent took to first touch a file in the gold patch: "context files, even developer-provided ones, are not effective at providing a repository overview". A second experiment is more telling for em. When the authors deleted every `.md` file and the `docs/` folder from the repositories, generated context files _started_ to help — which means the agents had been reading the documentation that was already in the tree, and the context file had only been duplicating it. Documentation present in the repository is found and read; that is the mechanism em's grep-able docs rely on.

Khatri (July 2026) compared no context file, the full file always in the system prompt, and on-demand retrieval of wiki pages, on Claude Code and Codex over 288 runs, and found no measurable difference in correctness between the three. Failure triage showed the agents failed on implementation skill — design, pattern selection, wiring — not on missing repository knowledge.

Maps also carry the highest maintenance cost. Tan, Wagner and Treude (2023) measured outdated code-element references in the READMEs and wikis of the top 1,000 GitHub projects: 3.9% of references were dead, 19.2% of documents and 28.9% of projects had at least one. Fluri et al. (2007) found that 97% of comment changes happen in the same revision as the code change — which is exactly the discipline `docs-sync` enforces — but that newly added code "barely gets commented". The thing that rots is the concrete reference to code, which is what a map is made of.

None of these studies measures what em imported its docs to fix. SWE-bench-style success rates reward a correct patch; they do not penalize an agent that writes a second implementation of a helper that already exists. Discussion #4190 named "reinventing existing infrastructure" as the failure, and the `plan` skill's build-versus-extend decision rests on the map. The evidence says maps do not make agents faster at finding files. It says nothing yet about whether they make agents extend rather than duplicate, which is a different outcome and the one this project cares about.

### 2.3 Lessons and rationale: the highest-value content, and the hardest to recover

The software-engineering literature on rationale predates agents and is unambiguous. LaToza, Venolia and DeLine (ICSE 2006) surveyed developers at Microsoft: 66% agreed that "understanding the rationale behind a piece of code" was a serious problem, the most serious of every problem surveyed, and 82% said it takes a lot of effort to understand "why the code is implemented the way it is". "Contrary to expectations that documentation makes understanding design rationale easy, we found that current design documents are inadequate." Ko, DeLine and Venolia (ICSE 2007) found "why was this code written this way" among the information needs most often deferred and never satisfied. Even projects that adopt architecture decision records drop the sections that carry the reasoning: a 2026 mining study reports "Decision Drivers" and "Considered Options" as the most often omitted.

The agent-memory literature says what kind of knowledge transfers between sessions. ReasoningBank (Google, 2025) distils items from both successes and failures and turns failures into preventative lessons; it raised WebArena success by 8.3 points and SWE-bench Verified from 34.2 to 38.8 while reducing steps, and beat both raw-trajectory memory and workflow memory. Reflexion (2023) is built entirely on verbal reflections about failed attempts. SWE-Exp (2025) banks failed as well as successful repair attempts. What transfers is abstracted, situation-conditional knowledge — a lesson, a constraint, a verified procedure — not transcripts and not summaries of what the code is. Shepard and Albrecht (June 2026) make the same point for guidance files: guidance refined against observed failures lifted a small model from 25.5% to 33.0% on SWE-bench Verified, where a one-shot generated knowledge base reached 28.3%. "How guidance is produced matters more than whether it exists."

Two opposite ways ruin a store of lessons. Xiong et al. (2025) show that unvetted records propagate errors: an agent copies a bad memory as readily as a good one, and selective add-and-delete beat naive growth by 10 points. And Agentic Context Engineering (Zhang et al., Stanford and SambaNova, 2025) shows that _compressing_ lessons destroys them: optimizers that "prioritize concise applicable instructions over comprehensive accumulation" drop the domain heuristics and failure modes that made the context useful, and a single monolithic rewrite collapsed an 18,282-token context to 122 tokens and accuracy from 66.7 to 57.1, below the no-context baseline. Their fix is itemized bullets with incremental updates, and it beat the best alternatives by 8 to 10 points. For the consuming model, long structured lessons beat short summaries. That is the strongest evidence for comprehensiveness in the literature, and it is about lessons, not maps: it holds when the content is genuinely new to the model.

### 2.4 Delivery: on demand costs less, works as well, and needs a named trigger

On-demand documentation matches always-on for correctness (Khatri) and costs less. Lulla et al. (January 2026) measured a 28.6% lower median runtime and 16.6% fewer output tokens with a curated `AGENTS.md` across 124 pull requests. Cochran (July 2026) ran a preregistered ablation over a 709-page LLM-maintained wiki and found progressive disclosure saved roughly a third of the cost for a capable self-routing agent, the saving coming from more targeted reads rather than from avoiding an index load. A July 2026 study of progressive disclosure at library scale concluded that "the useful pattern is a flat routing layer with content loaded on demand", and that extra routing depth has its own context cost. Anthropic's Agent Skills design is the same shape: names and descriptions always loaded, bodies on demand, so "the amount of context that can be bundled into a skill is effectively unbounded".

The cost of always-on context is not hypothetical. Chroma's Context Rot report (2025) measured eighteen models and found all of them degrade as input grows "even on trivial tasks"; a focused prompt of about 300 relevant tokens beat the full 113,000-token prompt in every model family, and a single distractor measurably hurt. NoLiMa (ICML 2025) found eleven of thirteen long-context models fell to half their short-context score by 32,000 tokens when the answer required inference rather than lexical match. A 26,000-token required read is a quarter of that budget spent before the agent has opened a source file.

The failure mode of on-demand delivery is equally well documented: the agent does not fetch what it does not know it needs. In Vercel's evaluation of Next.js 16 APIs that post-date model training, a skill containing the answers was never invoked in 56% of cases and moved the pass rate from 53% to 53%; one instruction telling the agent to prefer retrieval raised it to 79%; and an 8 KB index in `AGENTS.md` pointing at on-demand documentation files reached 100%. Vercel's own explanation is that "there's no moment where the agent must decide 'should I look this up?'". A later re-analysis found the improvement concentrated in a few tasks, and 17.7% of test pairs flipping from fail to pass rather than a universal effect, but the mechanism stands. A UCSB study of 34,000 real skills found their benefit "fragile: performance gains degrade consistently as settings become more realistic, with pass rates approaching no-skill baselines" once retrieval is left to the agent. The lesson is not that on-demand fails; it is that the trigger must be named where the agent will see it. em's `plan` skill, which makes specific documents mandatory reading, is that trigger.

### 2.5 Maintenance: stale is worse than absent, and growth has no natural limit

Practitioners agree on this more than on anything else. Cloudflare's internal engineering stack post (July 2026): "A stale AGENTS.md can be worse than no file at all." Datadog's repository instructions carry the clause "stale guidance causes recurring mistakes across sessions". Focused Labs: documentation drift "used to be a tax and with coding agents it becomes a runtime defect that the team has to own", because a wrong assumption "gets serialized in a diff and it looks productive". The DeepWiki backlash of 2025 — an auto-generated wiki asserting that LibreOffice builds with Buck — is the cautionary case for generated system explanations with no repair loop. This is the case `docs-sync` already makes for itself, and the co-change data in §1.2 shows the loop runs.

On growth, the tool builders and the researchers say the same thing from different directions. Boris Cherny's advice is to add a line to `CLAUDE.md` whenever Claude makes a mistake and "ruthlessly iterate … until you see the mistake rate drop"; Mitchell Hashimoto says every line in Ghostty's `AGENTS.md` is a past failure, and keeps it at 22 lines. Addy Osmani recommends periodically deleting the whole file and rebuilding "only what matters", treating it as "a living list of codebase smells you haven't fixed yet". Anthropic deleted more than 80% of Claude Code's own system prompt for the Claude 5 generation "with no measurable loss", reporting that rules hand-tuned for older models "were actively getting in the way of the newer ones"; Kieran Klaassen, who created Compound Engineering, said after that release to "let go of your skills and big mega prompts". Every one of these is a deletion policy. CE's `ce-compound-refresh` is the only one that is a procedure with evidence rules rather than a habit.

### 2.6 What the practitioners add on comprehensiveness itself

The two most-cited arguments for comprehensive, maintained knowledge bases are Karpathy's "LLM wiki" pattern (April 2026) — raw sources compiled once into an interlinked markdown wiki that the model keeps current, "not re-derived on every query", with a lint pass for contradictions and stale claims — and Vercel's docs index. Both won on their own terms, and both were about knowledge the model could not get from the repository: external sources, and APIs newer than the training data. Implementers of Karpathy's pattern report the failure mode within months: "a compiled wiki can become confidently wrong. Once an unsupported answer is filed back into memory, later agents can treat the fabrication as a source", and the remedies converge on provenance — every claim traces to a source, lint findings must quote the text they judge. Nobody in the practitioner literature argues for re-explaining what `grep` reveals; the closest positions (Korolev, Ability.ai) argue that documentation should carry "ideas, goals, and principles rather than snapshots of current implementation" and that "intent is the layer the agent cannot reconstruct from code alone".

Every's own claims for Compound Engineering are experience reports without controlled comparison: "each feature makes the next feature easier to build", five products each run primarily by one person, and a demonstration of a learning captured once and applied 18 days later on unrelated work. The plugin's own pull request #879 is candid about the failure it fixes: "`/lfg` was linear and amnesiac: every run started from zero and ended teaching the next one nothing." That is a problem em's docs were built to prevent by other means.

### 2.7 What the evidence cannot say

The controlled studies measure resolution rate on Python bug-fix benchmarks with one sample per task; effects are small, agent-specific, and flip sign between studies (context files cost 20% more in one study and 28% less in another). Vendor evaluations are small and undisclosed. Nothing measures reuse, architecture quality, or whether an agent extended rather than duplicated, which is the outcome em's map exists to improve. And most of the work was done on models from 2025; the practitioner reports from mid-2026 all point the same way, toward newer models needing fewer rules and less scaffolding. Every recommendation below is weighted accordingly: none of them removes content, and each can be reversed.

## 3. em against the evidence

**Already right.** The always-on file is 631 words, under every published ceiling. Subsystem docs load on demand behind a named trigger, the `plan` skill, which is exactly the mechanism Vercel's and the UCSB results say on-demand content needs. Docs are repaired in the same commit as the code, and the measured drift rate (1.2% of cited paths) is a third of the published open-source baseline. Every skill and doc explains its reasoning, which Chakrabarti's data says is what keeps instructions followed and prunable, and `docs-sync` forbids deleting it. Skills sit under the 5,000-token cap Claude Code applies when re-attaching a skill after compaction (the largest, `write-issue`, is about 3,900 tokens), and a typical chain — `end-session`, `docs-sync`, `ci-monitor`, `test-diagnosis` — is about 7,400 tokens against the 25,000-token combined budget. Lessons are written with provenance, from observed failures, in the session that found them, which is the capture mode Shepard and Albrecht and the memory literature say transfers.

**Exposed.**

- **No bar for additions.** `docs-sync` decides _which_ docs a change touches and insists the edit describe the present, but nothing decides whether a new paragraph earns its place. Chakrabarti's growth curve applies: 77 commits to `testing.md` in four months, each adding and few removing.
- **The largest required read is mostly not about its trigger.** `testing.md` is 19,467 words. The "read in full before writing tests" instruction costs about 26,000 tokens, and the largest section, CI workflows at 6,831 words, describes superseded runs, Dependabot repair and Copilot conflict handling — needed by an agent debugging CI, not by one writing a test. Only 3.5% of the document is code, so this is not a matter of trimming examples; it is a routing problem. Both the context-rot data and the progressive-disclosure studies say the cost is real and the routing fix is cheap.
- **The no-history rule discourages the most valuable content.** "What didn't work" is the section the memory literature and CE both single out as the highest-value capture, and it is history by construction. em's docs do record rejected alternatives when they are phrased as present-tense constraints ("`touchstart` is not an alternative because…", "doing this from the prompt files instead was considered and rejected"), but `docs-sync` does not say that this is allowed, and an agent applying "not a changelog" literally will drop it.
- **Lessons without a home are dropped.** A lesson that passes CE's counterfactual but belongs to an area no subsystem doc covers has nowhere to go: `docs-sync` says to report the gap and not to write a new doc mid-session. That is the right rule for maps and the wrong rule for a two-sentence lesson.
- **Some standing instructions restate what a linter enforces.** `testing.instructions.md` bans `vi.waitFor` and `expect.poll`, which an ESLint rule already rejects; the doc's value is the _reason_ and the replacement, which the rule's message also carries. This is the most common smell in the 100-repository survey and a small cleanup.

## 4. Compound Engineering against the evidence

**Right.** The bar is the sharpest statement in the literature of what to write down, and it matches the evidence on rationale, failure-derived capture, and lint leakage. Itemized, frontmatter-tagged lessons are the shape ACE and ReasoningBank found to transfer. `ce-compound-refresh` is a deletion procedure with evidence rules, which nothing else in the field has. Grounding validation (cite the defining line; cite pull requests, not SHAs) is the provenance discipline the LLM-wiki implementers arrived at independently.

**Exposed.**

- **The store depends on a retrieval step.** A learning is found only if `learnings-researcher` runs and its grep matches the frontmatter. CE learned this the hard way (pull request #456) and now edits `AGENTS.md` to advertise the store. An agent without the plugin, or a plan that does not run the researcher, never sees it. em's lessons sit inside documents the `plan` skill already requires, and are hit by the same grep that finds code.
- **Organization by problem type scatters a subsystem's lessons.** Three lessons about touch handling could sit in `ui-bugs/`, `integration-issues/` and `conventions/`. An agent about to change touch handling has to search for them; an agent reading `cursor-and-caret.md` gets them in the paragraph about the mechanism they constrain.
- **Re-deriving the map every plan is a cost CE pays and does not measure.** `ce-plan` runs a repository research subagent on every plan. Gloaguen's redundancy experiment shows agents read in-tree docs when present; CE's design forgoes that in favour of fresh exploration, which is defensible for a fast-changing tree and expensive for a stable one.
- **CE's own instruction file ignores its own evidence.** Its always-on `AGENTS.md` is 5,249 words, more than eight times em's, in a project whose learnings record that always-on essays burn context.

## 5. Conclusion: complementary, with a specific blend

The four candidate conclusions, in order:

- **Adopt CE's non-obvious-exceptions strategy.** No. Taken literally it means deleting the map and re-deriving it every session. The evidence that maps do not help is about navigation speed on bug-fix benchmarks; the map here exists for build-versus-extend decisions, which nothing has measured, and the `plan` skill is built on it. CE itself keeps subsystem specs.
- **Keep our approach unchanged.** Not quite. Two of the exposed points, unbounded growth and a 26,000-token required read, have evidence behind them and cheap fixes.
- **Blend.** Yes, in one direction: CE's _bar_ and its _capture of failed approaches_ belong inside em's docs; CE's _store_ does not, because em lacks the retrieval step it needs and em's retrieval already finds lessons where they are.
- **Something more nuanced.** The nuance is the split by kind of content. Keep the standing instructions small. Keep the map, but stop it growing and keep it where the router looks (`folder-structure.md`, `glossary.md`, `readme.md`). Treat lessons as the asset: gate them with CE's counterfactual, write them beside the mechanism with provenance, sanction rejected alternatives, and prune with positive evidence.

## 6. Recommendations

Each is small, reversible, and stated with what it buys and what it costs.

1. **State the bar for what earns a paragraph.** Add to `docs-sync` step 3 and to `AGENTS.md`: a new passage earns its place when it records a constraint, an invariant, a rejected alternative, or a reason the code does not state; a passage that restates what a test, a type, a lint rule or a comment already says belongs there instead. Adopt CE's counterfactual verbatim. _Buys_ a growth limit with a rule agents can apply. _Costs_ one more judgment at `docs-sync` time.
2. **Sanction "what did not work".** Amend the "not a changelog" rule: a failed approach or rejected alternative is design intent, not history, when written as a present-tense constraint that says why the alternative fails, as the toolbar-dropdown paragraph does. Changelog phrasing ("previously", "as of #…") stays banned. _Buys_ the highest-value capture the literature identifies. _Costs_ nothing; it describes current practice.
3. **Add a routing layer to `testing.md`.** Move the CI workflows section into its own document (it is about CI, not about writing tests) and change the instruction from "read in full" to "read Principles, Test Levels, Test Helpers and Sanctioned Backdoors, and the section for the level you are writing". `testing.instructions.md` remains the always-on rules layer. One level of routing, no hierarchy. _Buys_ roughly a halving of the per-session read for test-writing tasks. _Costs_ the risk that a rule in a section not read is missed; the mitigation is that every rule is already summarized in `testing.instructions.md`, and the sections that carry rules stay required.
4. **Give a homeless lesson a home without a second store.** Change `docs-sync`'s gap rule for lessons: a lesson that passes the bar but has no subsystem doc goes into `glossary.md` as an entry under the term it is about, or into the nearest doc's section, in the same commit. Only if this happens often enough that the glossary fills with pitfalls is a `docs/solutions/`-style store worth its retrieval step. _Buys_ zero lost lessons. _Costs_ a small drift in what the glossary is for.
5. **Run a periodic worth audit.** Once a quarter, or when a doc passes a size threshold, run the equivalent of `ce-compound-refresh`'s worth lens over `docs/`: prune passages whose every claim is now stated by a named test, type, lint rule or comment, with the artifact quoted; check every cited path; check for contradictions between docs. This could be a `docs-audit` skill or a section of `docs-sync` that runs on request. _Buys_ a deletion policy, which every practitioner recommends and none of them has as a procedure. _Costs_ one session a quarter.
6. **Keep the map, but stop growing it.** A subsystem doc adds mechanism description only when it anchors a constraint or a reason. File-by-file listings live only in `folder-structure.md`. Nothing is deleted on the strength of the navigation studies, because they do not measure what the map is for.
7. **Trim lint leakage from the standing instructions.** Where an instruction restates a rule ESLint enforces, keep the reason and the replacement and drop the restatement. _Buys_ a few hundred always-on tokens. Low priority.

## 7. Signals to watch instead of running evaluations

None of these requires an experiment; each is a count that can be taken from history or from transcripts.

- **The `docs-sync` outcome ratio.** The share of sessions that end with `docs: updated` versus `docs: unaffected`. A rising share of updates on small changes suggests the docs are over-coupled to code; a falling share on large changes suggests drift.
- **The dead-path rate.** Currently 1.2% of 332 cited source paths. The published baseline for open-source projects is 3.9%. The `docs-sync` path check already computes this.
- **The token cost of required reads.** The word counts of the documents a skill makes mandatory, per skill. `testing.md` is the outlier today.
- **Recurrence in a documented area.** A bug fixed twice in an area whose doc described the trap means the doc was not found, not read, or wrong. Each is a different fix.
- **Whether plans quote docs.** The `plan` skill requires quoting the relevant constraint. A plan whose quoted constraint changed the design is the map earning its place; a plan whose quotes are decorative is the map costing tokens.
